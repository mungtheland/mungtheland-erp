# Firestore 출석 영구 저장 사전 점검

이 문서는 직원 테스트 서버의 영구 저장을 별도로 승인받아 검증할 때 사용합니다. 기본 모드는 프로세스 메모리입니다. 테스트 서버에서 메모리와 Firestore의 출석 기록은 서로 이관되지 않습니다.

## 로컬에서 확인한 경계

| 항목 | 코드 동작 |
|---|---|
| 프로젝트 | 로컬 서버와 Firestore 어댑터는 코드에 고정된 테스트 프로젝트를 검사합니다. 정상 직원 서버에서 운영 프로젝트나 에뮬레이터 전용 프로젝트로 바꿀 수 없습니다. 에뮬레이터 시나리오는 별도 하네스에서 실행합니다. |
| 저장 플래그 | `MD_TEST_ATTENDANCE_FIRESTORE`의 명시적 활성화가 있어야 Firestore를 초기화합니다. 이 모드에서는 `MD_TEST_ATTENDANCE_PERSIST`와 `MD_TEST_ARRIVAL_WRITE`를 동시에 활성화할 수 없습니다. 예약 원장에는 읽기 전용 범위만 요청합니다. |
| 주소와 데이터베이스 | 클라우드 모드는 Firestore 또는 Auth 에뮬레이터 설정, 충돌하는 프로젝트 설정, 기본 데이터베이스 외의 대상, 비표준 엔드포인트·포트와 비보안 연결을 거부합니다. 검사에 실패하면 서버를 바인딩하기 전에 종료합니다. |
| 컬렉션과 쓰기 범위 | 기본 데이터베이스의 `attendance_test_v1/{bookingId}`를 사용합니다. `MD_TEST_ATTENDANCE_BOOKING_ID`에 지정한 가상 예약 1건만 직원 쓰기 경로에서 허용합니다. 이 설정은 예약의 가상 여부에 대한 운영 확인을 대신하지 않으므로 승인 전에 시트와 대조합니다. |
| 인증 주체 | 서버는 ADC를 사용합니다. 앱과 클라이언트 설정만으로 유효한 인증 주체와 권한 범위를 확정할 수 없습니다. |
| 보안 규칙 | 이 저장소에서 테스트 프로젝트에 게시된 규칙을 확인할 근거를 찾지 못했습니다. 서버의 Admin SDK 접근은 IAM으로 제한하고, 클라이언트의 직접 접근은 게시된 보안 규칙을 별도로 검토합니다. 예약 제한은 이 HTTP 경로에 적용됩니다. |

## 활성화 전 체크리스트

- [ ] 프로젝트 관리자가 서버·브라우저 인증·데이터베이스의 대상이 모두 동일한 격리 테스트 프로젝트인지 확인합니다. 기본 데이터베이스의 존재·위치와 네트워크 경로도 확인합니다.
- [ ] ADC의 유효 주체와 가장 권한을 확인하고, 대상 주체가 운영 리소스에 접근하지 않는지 확인합니다. 테스트 Firestore 읽기 및 트랜잭션의 문서 생성·갱신에 필요한 권한만 사용합니다. 이 흐름은 삭제 권한을 사용하지 않습니다. 기존 Firebase Auth 검증 권한과 테스트 예약 원장의 읽기 전용 공유 범위도 확인합니다.
- [ ] 승인된 테스트 직원 매핑, 가상 예약·반려견 데이터, 선택한 예약의 현재 출석 기록과 승인된 시작 상태를 대조합니다. 기존 기록과 충돌하면 해당 테스트를 보류합니다.
- [ ] 게시된 규칙이 웹 클라이언트의 출석 컬렉션 직접 쓰기를 허용하는지 확인하고, 의도하지 않은 직접 접근이 가능하면 보류합니다. IAM 변경과 규칙 게시에는 별도 승인이 필요합니다.
- [ ] 에뮬레이터 설정이 비어 있고 출석용 Firestore 이외의 쓰기 플래그가 꺼져 있는지 확인합니다. 실행 승인에는 테스트 대상, 가상 예약 한 건, 쓰기 범위, 종료 조건을 명시합니다.

**이 단계에서 확인하지 않은 항목**은 실제 IAM과 ADC 유효성, 배포된 보안 규칙, 데이터베이스 존재·위치·네트워크 연결 및 실제 읽기·쓰기 결과입니다.

## 36단계 읽기 전용 진단

별도로 읽기 승인을 받은 세션에서 저장소 루트의 `node guardian-auth-server/firestore-readonly-diagnostic.js`를 실행합니다. 도구는 기존 ADC의 가장 대상을 확인하고, 지정된 테스트 프로젝트의 기본 데이터베이스와 출석 컬렉션만 조회합니다. 문서가 있으면 한 건의 메타데이터만 확인합니다. IAM의 정책 조회와 현재 권한 확인은 읽기 메서드이며, 게시된 Firestore 규칙은 릴리스와 연결된 규칙 집합을 조회하는 방식입니다.

결과에는 위치·상태·성공 여부와 허용된 오류 코드만 남깁니다. 권한 확인 결과는 프로젝트 범위의 응답이며 컬렉션별 쓰기 권한이나 보안 규칙의 효과를 보증하지 않습니다. 조회가 거부된 항목은 현재 권한으로 확인 불가입니다. 진단 실패 시 권한을 바꾸거나 다른 인증 주체로 전환하지 않습니다.

## 37단계 권한·규칙 판정

| 판정 | 확인 결과 |
|---|---|
| 확인됨 | 동일한 테스트 ADC로 기본 데이터베이스와 출석 문서를 읽었습니다. 프로젝트 범위 권한 응답에는 트랜잭션에 필요한 데이터베이스 접근과 문서 읽기·생성·갱신 권한, 진단용 목록 권한이 포함됐습니다. |
| 차단됨 | 프로젝트 IAM 정책과 게시 규칙 릴리스 조회는 현재 주체에 HTTP 403을 반환했습니다. 프로젝트 권한 조회 결과에도 해당 정책·릴리스 조회 권한이 포함되지 않았습니다. 로컬 CLI 캐시에서 사용 가능한 기존 관리자 세션을 확인하지 못했습니다. |
| 미확인 | 실제 IAM 바인딩과 상속·조건의 적용 범위, 게시된 규칙 본문과 웹 클라이언트 접근 효과, 실제 커밋 가능 여부는 확인하지 못했습니다. |

출석 서비스의 Firestore 트랜잭션에는 `datastore.databases.get`, `datastore.entities.get`, `datastore.entities.create`, `datastore.entities.update`가 필요합니다. 진단의 목록 요청에는 `datastore.entities.list`가 추가로 필요합니다. 데이터베이스 메타데이터 요청은 별도의 `datastore.databases.getMetadata`를 사용합니다. 출석 서비스에는 삭제, IAM 정책 변경, 규칙 게시 권한이 필요하지 않습니다. 프로젝트 권한 응답은 검사한 권한만 보여 주며 추가 권한의 유무나 범위를 확정할 수 없습니다. [Firestore 서버 권한 표](https://docs.cloud.google.com/firestore/native/docs/security/iam)

ADC를 사용하는 서버 Admin SDK는 IAM으로 평가됩니다. 웹 클라이언트의 직접 요청에는 게시된 보안 규칙이 적용됩니다. 서버 쓰기 권한의 확인으로 웹 직접 쓰기의 차단 여부를 판단할 수 없습니다. [Firestore 보안 규칙 안내](https://firebase.google.com/docs/firestore/security/get-started)

38단계에서는 기존 읽기 권한을 가진 프로젝트 검토자가 기본 데이터베이스의 실제 IAM 바인딩과 게시된 규칙을 조회해, 웹 클라이언트의 직접 출석 쓰기 허용 여부를 확인합니다. 규칙을 검토할 수 있게 되면 클라우드 쓰기 없이 격리 에뮬레이터에서 해당 조건을 재현합니다. 두 확인이 끝날 때까지 영구 저장 활성화를 보류합니다.

## 39단계 독립 쓰기 검증 도구

프로젝트 소유자와 현재 게시된 모든 웹·모바일 클라이언트 읽기·쓰기 거부 규칙은 사용자 확인 사항입니다. 이 단계는 해당 규칙을 변경하거나 실제 클라우드에 쓰지 않습니다.

`node guardian-auth-server/firestore-attendance-write-probe.js`는 기본적으로 목표만 표시하고 종료합니다. 기본 실행은 ADC와 네트워크를 사용하지 않습니다. 에뮬레이터 검증은 [기존 하네스](firestore-attendance-emulator.md)에서 실행합니다.

실제 클라우드 실행은 별도 승인 시에만, 명시적 실행 옵션과 승인된 테스트 프로젝트 ID를 함께 지정해 진행합니다. 옵션은 `--execute-approved-test-write`입니다. 대상은 지정된 테스트 프로젝트의 기본 데이터베이스와 출석 테스트 컬렉션으로 고정되며, 다른 프로젝트·데이터베이스·컬렉션이나 문서 ID를 인수로 지정할 수 없습니다.

1. 실행 직전 승인된 테스트 주체와 저장 플래그 비활성 상태를 확인합니다. 도구는 기존 ADC 대상, 에뮬레이터·프로젝트 충돌 여부, 데이터베이스 이름·리전·유형을 검사합니다. IAM 권한 확인에서 문서 읽기·생성·삭제가 모두 반환되는 경우에만 이어갑니다. 이 확인은 실제 삭제 성공을 보장하지 않으므로, 사전에 기본 데이터베이스에 적용되는 권한과 복구 담당자를 확인합니다.
2. 가상 직원과 임의의 테스트 예약 ID로 한 건을 구성합니다. 같은 ID의 문서가 있으면 중단하며, 읽기 이후 경쟁으로 문서가 생겨도 생성 API가 충돌을 반환합니다. 저장 시도 전에는 복구에 필요한 가상 문서 ID만 표시합니다.
3. 생성 응답과 다시 읽은 문서의 이름·전체 내용·갱신 시각이 같을 때만, 확인한 버전을 조건으로 삭제합니다. 삭제 확인은 같은 ID를 읽어 문서 없음이 반환됐는지 검사합니다.
4. 응답 유실, 내용이나 버전 변경, 실패가 있으면 자동 재시도나 추가 삭제 없이 중단합니다. 삭제가 확인되지 않았으면 승인된 담당자가 표시된 가상 ID로 읽기 전용 상태를 확인합니다. 도구가 생성 응답을 확인한 경우 실패 결과에 최초 갱신 시각도 포함됩니다. 별도의 복구 삭제는 그 실행이 만든 기록과 현재 버전의 일치가 확인되고 복구 승인이 있을 때만 검토합니다.

이 도구는 단일 가상 문서의 생성·조회·삭제를 분리 검증합니다. 기존 서버, 예약 원장과 출석 저장 플래그를 사용하지 않으며, 실제 직원 UI의 출석 저장 검증은 별도 범위입니다.

## 40단계 잔여 문서 확인과 수동 복구

**실제 실행 전 체크리스트**

- [ ] 승인 범위에 지정된 테스트 프로젝트, 기본 데이터베이스, 리전, 출석 테스트 컬렉션, 가상 문서 한 건과 그 문서의 조건부 삭제가 모두 포함돼 있습니다.
- [ ] 기존 테스트 ADC의 가장 대상, 에뮬레이터 미사용, 저장 플래그 비활성, 읽기·생성·삭제 권한과 적용 범위를 확인했습니다. 프로젝트 범위의 권한 응답은 실제 커밋이나 삭제 성공을 보장하지 않습니다.
- [ ] 실패 시 확인할 담당자와 승인 경로를 정했습니다. 로컬 기록에서 `create-attempt`의 가상 ID와 예상 해시, 그리고 수신한 경우에만 `create-confirmed`의 생성 버전을 보존합니다. GitHub에는 개별 실행 증거를 게시하지 않습니다.

**읽기 전용 확인**

`node guardian-auth-server/firestore-attendance-residue-check.js`의 기본 실행은 인증이나 네트워크 없이 종료합니다. 테스트 프로젝트 읽기가 승인된 경우에만 `--inspect` 뒤에 기록된 가상 문서 ID를 전달합니다. 예상 해시와 생성 확정 시각이 있다면 각각 두 번째와 세 번째 값으로 추가합니다. 생성 응답을 받지 못했다면 시각을 추정해서 넣지 않습니다.

```powershell
node guardian-auth-server/firestore-attendance-residue-check.js --inspect $probeId $expectedFingerprint $confirmedCreationVersion
```

도구는 고정된 테스트 데이터베이스의 단일 문서만 읽고, 존재 여부와 가상 픽스처·해시·버전의 일치 여부만 출력합니다. 문서 내용과 개인정보는 표시하지 않습니다. `absent`면 조회 시점에 잔여 문서가 없습니다. 생성 요청이 시간 초과됐다면 지연 커밋 가능성을 검토하기 전에 새 쓰기를 실행하지 않습니다. `blocked`나 `failed`는 부재가 확인된 상태가 아니므로 후속 쓰기를 중단합니다.

**수동 복구 승인**

1. 원래 실행의 `create-confirmed` 기록으로 ID와 예상 해시 및 생성 버전이 연결돼 있는지 확인합니다. 같은 ID의 문서가 존재하거나 해시만 일치한다는 사실은 삭제 근거로 사용하지 않습니다.
2. 읽기 전용 확인 결과에서 `evidenceMatches`가 참이어야 합니다. 증거가 없거나 파일럿 이후 내용·버전이 달라졌다면 보존합니다.
3. 별도 승인에는 정확한 테스트 대상, 문서 ID, 확인한 버전과 단일 삭제 작업을 기재합니다. 승인을 받은 담당자만 동일 버전 조건을 적용해 삭제하고, 읽기 전용 조회로 삭제 여부를 확인합니다. 조건 충돌, 권한 거부, 타임아웃이 발생하면 자동 재시도하지 않습니다. 기존 기록과 소유권이 불명확한 문서를 보호하기 위해 별도 복구 삭제 명령은 제공하지 않습니다.

## 승인 이후 실행과 롤백

1. 승인된 별도 PowerShell 세션에서 기존 테스트 인증 매핑을 준비하고, 테스트 프로젝트와 가상 예약 한 건을 지정합니다. 다른 쓰기 플래그는 비활성 상태로 두고 기존 서버와 겹치지 않는 루프백 포트를 선택합니다. 승인이 완료된 경우 `guardian-auth-server`에서 `npm.cmd start`로 시작합니다. 시작 로그의 저장 모드를 확인한 뒤 읽기만 수행해 대상과 초기 상태를 대조합니다.
2. 일치할 때만 승인된 요청을 순서대로 검증합니다. 대상 불일치, 인증·권한 오류, 결과 불명확이 발생하면 추가 쓰기를 중단합니다. 응답을 잃었다면 현재 상태가 확인될 때까지 다른 요청 ID로 재전송하지 않습니다.
3. 롤백은 새로 시작한 검증 세션만 중지하고 그 세션의 Firestore 플래그와 예약 제한 설정을 해제하는 절차입니다. 필요 시 별도 승인된 절차로 메모리 모드에서 재개합니다. 서버 모드 전환은 이미 커밋된 이력을 삭제하거나 되돌리지 않습니다. 불명확한 기록은 보존하고 별도 검토로 넘깁니다.
