# 멍더랜드 ERP MVP 구현 계획

## 목적과 범위

A안에 따라 신규 고도화보다 기존 Apps Script ERP와 직원 서버를 재사용해 유치원 운영의 핵심 업무를 안전하게 연결한다. 기존 운영 기능은 삭제하거나 임의로 비활성화하지 않는다. 계획은 2026-11-28의 저장소 감사 결과를 바탕으로 하며, 외부 서비스 접근·클라우드 변경·배포는 포함하지 않는다.

우선 필수 범위는 입소/계약, 결제/할인, 이용권, 예약, 출결, 회계, 권한, 백업이다. 알림장 고도화, 카카오 자동 발송 확대, 고급 통계, 비필수 UI 확장은 2차로 연기한다. 보안·접근성·오류 안내·복구처럼 핵심 흐름의 안전성에 필요한 화면 작업은 MVP에서 제외하지 않는다.

## 선행 의존성

```text
운영 정책·데이터 소유자 확정
        ↓
개인별 인증·최소 권한·시험/운영 환경 경계
        ↓
입소/계약 및 결제 증빙 계약
        ↓
승인 상품 카탈로그 + 영속 발급 ID/이력
        ↓
예약 ↔ 보호자/반려견/이용권의 정확 ID 연결
        ↓
등원·하원 ↔ 차감/복구 부분 실패 처리
        ↓
회계 대사·정산 승인 및 백업/복원 운영 증거
        ↓
격리 E2E 인수시험 → 운영 준비 검토 → 별도 배포 승인
```

순서는 중복 발급과 잘못된 이용권 차감을 막기 위해 상품·결제·ID 계약을 먼저 확정하도록 구성했다. 권한, 백업, 개인정보 절차는 마지막에 덧붙이는 작업이 아니라 실데이터 시험 전부터 병행해야 하는 출시 게이트다.

## 예상 잔여 작업량

- 검증된 사실: 현재 CI 스크립트는 예약/변경, 수동 이용권, 등·하원, 회계/정산, 백업, 발급 모듈의 로컬·합성 테스트를 실행한다. 실운영 전 점검 문서는 `NO-GO`이며, V2 발급 환경과 카탈로그/결제 연결은 활성화되지 않았다.
- 추정치: 위 개발 작업의 합은 약 **20–38 인일**이다. 한 명의 저장소 숙련 개발자가 기존 코드를 재사용하고, 범위가 유지된다고 가정한 공학 작업량 추정이다. 정책 승인, 법률/회계 검토, Google/Tally/결제 사업자 설정, 접근 권한, 실제 주기 백업 관찰, 사용자 인수시험 대기 시간은 포함하지 않는다.
- 달력 완료일은 제시하지 않는다. 정책과 외부 자원 승인이 필요한 기간은 저장소 근거만으로 예측할 수 없다.

## 실운영 전 최종 검수 체크리스트

### 정책과 데이터 계약

- [ ] 계약·취소·환불·할인·일일권/정기권 정책이 승인되고 고객 안내와 ERP가 일치한다.
- [ ] 예약, 고객, 반려견, 상품, 이용권, 결제 참조 및 발급요청 ID가 각 원장에서 정확히 연결된다.
- [ ] 상품 카탈로그의 운영 상품 ID·회차·가격·차감 정책이 권한 있는 소유자에 의해 승인된다.
- [ ] 기존 ID 누락·중복·과거 결제 참조 미확인 기록의 처리 책임과 예외 절차가 정해졌다.

### 인증·권한·개인정보

- [ ] 관리자/직원/보호자가 개인 인증을 사용하고 각 요청에서 역할·소유권을 서버에서 재검증한다.
- [ ] 최소 권한, 계정 폐기, 세션 만료, 비밀 저장, 감사 로그 및 권한 검토가 확인됐다.
- [ ] 개인정보 고지, 필수/선택 항목, 보유·파기, 요청 처리, 사고 대응 및 외부 처리자 범위가 승인됐다.
- [ ] 로그와 보고서에 토큰·비밀번호·결제 세부정보·불필요한 고객정보가 포함되지 않는다.

### 핵심 흐름과 정합성

- [ ] 입소/계약 → 결제 확인/할인 → 이용권 발급 → 예약 → 등원/차감 → 하원 → 회계/정산까지 격리 E2E로 대조된다.
- [ ] 동일 요청, 다른 요청 ID의 동일 결제, 동시 실행, 응답 유실, 부분 쓰기, 재시작에서 중복 발급/차감이 없다.
- [ ] 차감 실패는 출석을 되돌리지 않고, 모호한 결과는 자동 재시도 없이 검토 상태로 남는다.
- [ ] 수정/취소/복구/정산 정정에는 적절한 권한, 사유와 감사 이력이 있다.
- [ ] Sheets·Firestore·결제 증거 사이의 정확 ID 매칭과 불일치 처리 기준이 검증됐다.

### 운영·복구·배포

- [ ] 정기 백업과 누락 알림이 실제 스케줄로 한 차례 이상 성공했고 증거가 대조됐다.
- [ ] 지정 담당자가 별도 사본에서 복원하고 업무 데이터·수식·접근권한·전환 절차를 확인했다.
- [ ] 비상 연락, 장애 시 거래 중지, 재조정, 수동 복구 승인, 고객 안내 및 담당자 인수인계가 준비됐다.
- [ ] 빌드 산출물과 배포 대상이 검토됐으며 운영 배포는 명시적으로 승인됐다.
- [ ] 제한된 파일럿을 통해 실제 운영자가 수락하고, 실패 시 중단/보존 절차가 실행 가능하다.
