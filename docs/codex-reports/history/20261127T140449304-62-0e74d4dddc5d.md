## Change summary

- Logical tab _이용권발급이력 is specified with 16 ordered Korean headers; string identifiers, integer versions and counts, ISO UTC request and commit times, enumerated status and fixed-code error field.
- Exact unique keys are issuance request ID, idempotency key, payment reference and pass ID. No whitespace or case normalization is used; the idempotency key binds catalog version and request ID.
- State lifecycle is VALIDATED to PENDING to COMMITTED. Partial or unknown states require NEEDS_REVIEW; FAILED_FINAL is terminal. A pending row reserves its planned pass ID before the pass row is appended.
- The private Apps Script adapter uses ScriptLock with a five-second wait, re-reads both tabs under lock, compares the pending row identity and status before updating, flushes each write, verifies the pass row, then marks and re-reads COMMITTED.
- The source-level switch is false and the private entry returns DISABLED before opening a workbook. The adapter does not create the proposed tab and has no public endpoint.
- The existing 이용권관리 schema has no legacy request or payment reference. The live port therefore reports incomplete historical payment coverage and blocks new issuance. Existing exact committed pairs remain lookup-only.
- Read-only reconciliation reports MATCH, NO_MATCH, DUPLICATE, MISMATCH, PARTIAL or NEEDS_REVIEW. It joins by exact pass ID and checks product ID, pet ID and use counts without repair.
- Faults before or after PENDING, pass append, commit marker and readback return review states; no retry automatically creates a replacement pass. Existing mdRegisterPass and the live workbook were unchanged.
- Architecture A keeps Sheets as balance source and adds an append-only issue journal with LockService and reconciliation; recommended for compatibility but it is not transactional. B leaves a Firestore marker with a non-atomic Sheets projection. C dual-writes both stores and has the greatest partial-write and reconciliation risk. No architecture was switched.
- The base adapter and CI registration were added in implementation commit b1c177bbefff7546f58277664918d85ab5e4419c; this follow-up hardens command validation, pass row compatibility and conditional marker updates.

## Remaining risks

- ScriptLock only serializes cooperating executions in the same Apps Script project; it does not provide multi-sheet atomicity or protect external editors and other projects.
- A process failure can leave a PENDING row or incomplete pass row. The adapter blocks retries and requires read-only reconciliation; automated repair is not enabled.
- Legacy payment references cannot be cross-checked from the current pass schema, so new live issuance remains blocked even if the source switch were changed.
