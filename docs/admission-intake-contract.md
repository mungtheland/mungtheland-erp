# 입소 신청·계약 데이터 계약 초안

**상태: 로컬 설계 초안, 운영자 승인 전.** 이 문서는 Tally 연결, 계약 체결, 개인정보 동의 수집 또는 원장 저장을 구현하지 않는다. 현재 코드에서 관찰된 입력과 제안 계약을 분리한다. 정책 결정이 필요한 값은 미확정으로 남긴다.

## 확인한 기존 구조

`src/Code.js`의 `MD_SCHEMAS['고객·반려견관리']`는 고객/반려견을 한 행에 저장한다. `mdRegisterDog(data)`에서 필수 검사되는 입력은 `guardianName`, `phone`, `dogName`이다. `customerId`는 전달되면 사용하고 없으면 서버 코드가 생성하며, `dogId`, 등록일과 상태도 코드가 생성한다. 견종, 생년월일, 성별, 중성화, 체중, 접종, 건강·알레르기, 주의사항, 비상연락처는 저장 열에 있지만 해당 함수의 필수 입력 검사는 아니다.

`src/Index.html`의 현재 내부 직원 등록 화면은 보호자명·연락처·반려견명을 필수 표시하고, 견종·비상연락처·건강·주의사항을 선택 입력으로 노출한다. 이 화면은 입소 신청서나 계약서 동의 화면이 아니다. 담당자 선택 UI 값이 `mdRegisterDog` 호출 인자로 전달되지 않으며, 등록 함수 인자에 검증된 직원 principal도 없다. 따라서 선택된 담당자 이름을 서버 인증이나 감사 증거로 취급할 수 없다.

`MD_SCHEMAS`에는 입소 신청, 계약 버전, 개인정보 안내 확인/동의 증거, 신청 상태, 수정 revision, 철회 접수 필드가 없다. 별도 신청 원장·Tally 제출 처리 코드도 확인되지 않았다. 기존 고객/반려견 시트에 열을 추가하거나 기존 기록을 신청으로 간주하지 않는다.

## 필드 계약 대조표

| 논리 필드 | 현재 코드/화면 근거 | 현재 입력 조건 | 입소 신청 계약 제안 | 확정 상태 |
|---|---|---|---|---|
| guardianName / 보호자명 | `MD_SCHEMAS`의 `보호자명`; `mdRegisterDog` 및 화면 입력 | 함수와 화면에서 필수 | 접수 시점에 수집할지와 본인확인 방법 결정 | 기존 등록은 확인, 신청 요건은 승인 필요 |
| phone / 연락처 | `MD_SCHEMAS`의 `연락처`; `mdRegisterDog` 및 화면 입력 | 함수와 화면에서 필수 | 신청자 연락 수단 및 검증 시점 결정 | 기존 등록은 확인, 신청 요건은 승인 필요 |
| emergencyPhone / 비상연락처 | 스키마 열과 함수 인자 존재; 화면에 선택 입력 | 함수에서는 선택 | 실제 응급 연락에 필요한지, 별도 연락 대상의 고지/근거 확인 | 필수성 승인 필요 |
| dogName / 반려견명 | 스키마 열; 함수 및 화면 입력 | 필수 | 신청 반려견의 표시 정보 | 기존 등록은 확인, 신청 요건은 승인 필요 |
| breed, birthDate, sex, neutered, weight | 스키마 열과 함수 인자 일부 존재 | 함수에서 선택; 현 화면 일부 미노출 | 안전·돌봄 목적별 필요성에 따라 선택 범위 결정 | 운영 정책/최소수집 검토 필요 |
| vaccines, health, notes | 스키마 열과 함수 인자 존재; 현 화면은 health/notes 일부 노출 | 함수에서 선택 | 필요한 건강/접종 증거의 범위, 파일 보관 여부 및 검토자를 결정 | 필수성·수집 범위 승인 필요 |
| customerId | 스키마 열; 함수는 입력값이 없을 때 신규 ID 생성 | 선택 입력/서버 생성 | 검증된 보호자 계정과 기존 고객 레코드 연결 | 계정 연결 증거 및 중복 처리 미확정 |
| dogId, registeredAt, status | 함수/기존 스키마 | 서버 코드 생성 | 신청 승인 이후 생성 시점과 중복 등록 규칙 결정 | 현재 입소 신청 상태와 연결되지 않음 |
| applicationId | 기존 코드에 없음 | 없음 | 신뢰된 서버가 첫 접수 시 발급하고 재전송에 동일 값 사용 | 새 계약 제안, 형식/고유 범위 승인 필요 |
| revision | 신청 원장에 없음 | 없음 | 수정 요청에 기대 revision을 요구하고 충돌은 재조회 유도 | 동시 수정/수정 허용 기간 승인 필요 |
| applicationStatus | 신청 상태 필드 없음 | 없음 | 상태 전이표 승인 전 저장/전이하지 않음 | **미확정** |
| contractVersion / acceptedAt / acceptanceEvidence | 계약서 초안의 서명·체결 정보만 제시 | ERP 필드 없음 | 정확한 문서 버전, 주체 연결, 시각, 확인 방식 및 증거 참조를 묶어 불변 기록 | 계약 형식·전자증거 기준 승인 필요 |
| privacyNoticeVersion / noticePresentedAt / legalBasis / consentEvidence | 개인정보 안내 초안에 버전/시각/선택 동의 기록 설계가 있음 | ERP 필드 없음 | 안내 확인과 동의를 분리하고 선택 동의는 항목별로 별도 기록 | 필수/선택 및 법적 근거 승인 필요 |
| sourceChannel / receivedAt | 신청 접수 경로가 확정되지 않음 | 없음 | 실제 연동된 채널과 서버 접수시각을 기록 | Tally 포함 접수 경로 미확정 |
| withdrawalRequest / withdrawnAt / handlingEvidence | 개인정보 절차에 권리 요청 처리 기록 필요가 기재됨 | ERP 필드 없음 | 철회/삭제 요청을 접수·검토·처리하고 보존 예외와 결과를 별도 추적 | 처리 대상·효력·보존 예외 승인 필요 |

## 제안 데이터 묶음 — 구현 전

신청 레코드와 계약/개인정보 증거를 분리하는 방안을 제안한다. 아래는 저장 계약 후보이지 현재 데이터 모델이 아니다.

| 묶음 | 후보 필드 | 안전 규칙 |
|---|---|---|
| 접수 envelope | `applicationId`, `revision`, `status`, `receivedAt`, `sourceChannel` | ID는 신뢰된 서버가 발급하고 재전송 시 유지한다. 상태 목록과 revision 정책은 승인 전 활성화하지 않는다. |
| 신청자 연결 | 검증된 `customerId` 또는 미연결 접수 식별자 | 클라이언트가 보낸 ID만으로 소유권을 인정하지 않는다. 이름·전화번호만으로 기존 계정/고객을 자동 결합하지 않는다. |
| 반려견 정보 | 기존 고객·반려견 스키마에 매핑 가능한 최소 필드 | 기존 고객/반려견 레코드에 새 필드를 강제하거나 자동 중복 생성하지 않는다. 선택/필수성은 안전 목적과 개인정보 검토 후 승인한다. |
| 계약 증거 | `contractVersion`, `acceptedAt`, 확인 주체, 확인 방식, 증거 참조 | 서명/전자 확인의 효력과 계약 사본 보존 방법을 승인한다. 계약 텍스트 자체를 로그에 남기지 않는다. |
| 안내 및 선택 동의 | 안내문 버전·표시 시각, 항목별 법적 근거/선택 여부, 응답·시각·철회 증거 | 안내 확인을 포괄 동의로 처리하지 않는다. 사진·홍보 동의 등 선택 항목을 기본 선택하지 않는다. |
| 수정/철회 이력 | 기존 값 스냅샷 참조, revision, 요청 시각, 검토 주체, 처리 결과 | 변경은 감사 가능한 새 revision으로 기록한다. 철회는 자동 삭제/계약 취소와 동일시하지 않으며 보존 의무를 검토한다. |

### 상태와 전이

현재 입소 신청 상태와 전이 계약은 없다. `RECEIVED`, `NEEDS_REVIEW`, `APPROVED`, `CONTRACTED`, `REJECTED`, `WITHDRAWAL_REQUESTED`, `WITHDRAWN`은 논의용 후보일 뿐 확정 enum이 아니다. 승인 전에는 기존 ERP 상태에 이를 매핑하거나 실제 기록에 사용하지 않는다.

수정 시 허용 시점·승인자·이전 계약의 효력, 신청 철회와 계약 해지의 차이, 개인정보 삭제 요청의 처리 순서와 법정/회계 보존 예외를 운영자 및 적절한 검토자가 결정해야 한다. 원본 신청이나 이미 체결된 계약을 덮어쓰거나 삭제하는 흐름은 이 계약에 포함하지 않는다.

## 동의 증거와 서버 검증 주체

`docs/customer-privacy-notice-draft.md`는 사업자/처리 책임자, 필수·선택 항목, 처리 근거, 보유기간, 외부 처리 관계가 확정되기 전 고객 배포 금지라고 명시한다. 안내를 봤다는 표시는 모든 처리에 대한 동의가 아니며 사진/홍보 선택 동의는 분리해야 한다. 그러므로 이번 단계에서는 동의 필드 이름과 증거 모양만 제안하고 체크 여부·법적 근거를 확정하지 않는다.

입력 브라우저는 신뢰 경계가 아니다. 실제 보호자 계정이 도입되면 서버는 검증된 인증 주체에서 고객 계정 연결을 해석하고 매 요청에서 보호자-반려견 관계를 확인해야 한다. `guardian-auth-server/authenticate.js`는 프로토타입용 서버 인증 계약을 가지지만 `docs/guardian-production-auth-design.md`는 보호자 운영 로그인과 배포가 미구현이라고 한다. 직원 검토/승인은 서버가 검증한 직원 principal로 수행해야 한다. 현재 `mdRegisterDog` 및 내부 UI의 담당자 선택만으로는 이를 입증하지 못한다.

## 합성 계약 테스트와 안전 경계

`tests/fixtures/admission-contract.fixture.json`은 `SYNTHETIC_ONLY` 값만 포함한다. `tests/admission-contract.contract.test.cjs`는 기존 고객/반려견 열과 필수 입력 검사를 소스에서 대조하고, 신청/동의/상태 정책이 미승인일 때 fixture를 활성 계약으로 오인하지 않는지 확인한다. 이 테스트는 애플리케이션 구현이나 실제 사용자 흐름의 검증이 아니다.

이번 단계에서 Tally/API, Sheets, Apps Script, Firebase 또는 클라우드 저장소를 호출하지 않는다. 새 시트·열·계정·계약 상태를 만들지 않는다.

## 다음 게이트

1. 운영자가 신청 접수 채널, 보호자 본인확인/대리 신청, 필수·선택 필드와 반려견 안전에 필요한 증거를 결정한다.
2. 계약 버전 관리와 체결 증거의 승인 기준 및 사본 제공 방식을 결정한다.
3. 개인정보 처리 근거, 동의 항목, 보유/파기, 수정·철회·삭제 요청과 보존 예외를 승인한다.
4. 신청 상태, 수정 가능 시점, 계약 체결 후 취소/철회 처리, 직원 검토 책임자를 승인한다.
5. 위 결정을 받은 후에만 Tally 또는 다른 접수 어댑터, 서버 검증 및 별도 격리 저장 모델을 구현한다.
