# 직원 출석과 이용권 차감의 읽기 전용 계약

## 확인한 환경

| 구분 | 저장소에서 확인한 경로 | 50단계 접근 |
| --- | --- | --- |
| 운영 예약·이용권 | `src/Code.js`의 원장 참조와 `src/PassAdjust.js`의 Apps Script 수동 차감·복구 | 원장 파일 참조는 코드에 있습니다. 승인된 읽기 주체, 실제 파일 공유 범위, 배포 설정, 실제 컬럼과 데이터는 미확인입니다. |
| 직원 서버 | Firebase 검증과 활성 직원 매핑을 거쳐 루프백 API 실행. Sheets 예약 조회는 고정된 격리 원장에 연결 | 기존 브라우저 로그인·예약 연결과 운영 차감 간에 승인된 서비스 호출 경로가 없습니다. |
| 출석·차감 상태 | Firestore 격리 프로젝트의 출석 문서, 49단계 모의 Apps Script 및 에뮬레이터의 발송 상태 | 50단계는 이미 저장된 출석을 읽어 대조합니다. 이용권 잔여·이력은 Sheets에서 읽습니다. |
| 노트북 인증 | 기존 기본 ADC 파일 존재와 사용자 유형을 로컬에서 확인 | 승인된 운영 파일 뷰어임을 입증하는 설정이 없어 Google Cloud 및 Workspace 요청을 실행하지 않았습니다. |

기본 직원 서버의 기존 격리 Sheets 쓰기 옵션은 기존 테스트 기능 전용입니다. 운영 원장 접근 권한을 별도로 확인해야 합니다. 테스트용 스프레드시트와 실제 운영 스프레드시트, 격리 Firebase 프로젝트와 합성 에뮬레이터는 승인 범위를 따로 관리합니다.

## 진단에 필요한 원장 필드

예약 ID로 정확히 한 예약을 찾고, 그 행의 이용권 ID로 정확히 한 이용권을 찾습니다. 예약과 이용권의 반려견 ID가 동일해야 합니다. 예약별 순차감은 해당 ID의 전체 변동이력으로 검사합니다. 잔여는 이용권 발급 후 전체 이력에서 검증하며, 다른 예약에서 같은 이용권을 정상적으로 사용하는 경우도 이 이력에 포함합니다.

| 시트 | 읽기에 필요한 열 |
| --- | --- |
| 예약·등하원관리 | A 예약 ID, B 이용일, C 반려견 ID, E 이용권 ID, F 예약 상태, G–H 등·하원 시각, I 출석 상태, J 차감 상태 |
| 이용권관리 | A 이용권 ID, B 반려견 ID, C 상품 ID, F–H 총·사용·잔여 횟수, I–J 시작·만료일, N 결제 상태, O 이용권 상태 |
| _이용권변동이력 | A 이력 ID, C 유형, D 이용권 ID, E 예약 ID, F 증감, G–H 이전·이후 잔여, I–J 자동 차감 실행 유형 및 이벤트 연결 증거 |

예약·이용권의 열 이름과 위치는 소스의 스키마와 대조했습니다. 변동이력의 위치는 쓰기 배열과 기존 조회 코드를 기준으로 확인했습니다. 실제 변동이력 헤더 문자열은 승인된 원장 사본에서 확인하고 어댑터의 허용 목록에 명시해야 합니다. 합성 헤더는 실제 원장의 증거로 사용할 수 없습니다.

승인된 운영 읽기를 추가할 경우 뷰어 권한의 전용 주체와 파일 허용 목록을 우선 사용합니다. Sheets OAuth의 읽기 범위는 파일 단위이므로 필요한 열만 고르는 처리는 읽기 어댑터가 맡습니다. 예약과 연결 후보 전체, 해당 예약과 이용권의 관련 이력 전체를 검사할 수 있는 경우에만 스냅샷을 완전하다고 표시합니다. 행 제한에 걸리거나 서로 다른 시점의 자료가 섞인 경우에는 판정을 차단합니다. 날짜는 서울 기준 ISO 날짜로, 횟수는 정수로 전달합니다. 이름·연락처·메모를 요청하거나 출력하지 않습니다. 이력 행의 사용자 표시와 사유는 어댑터에서 자동 실행 표시와 검증에 필요한 작업 증거만 남깁니다. [Google Sheets 권한 범위](https://developers.google.com/workspace/sheets/api/scopes)

## 서버 간 인증 계약 초안

1. 직원 화면에서 보낸 Firebase ID 토큰은 기존 직원 서버가 검증합니다. 대상 프로젝트, 유효기간, 취소 여부, 이메일 검증과 활성 직원 매핑을 통과해야 합니다. 브라우저에서 직접 Sheets 또는 Apps Script를 호출하지 않으며, 직원 증명은 Apps Script 관리자 권한으로 전달하지 않습니다.
2. 서비스 간 채널은 전용 호출 주체의 서명을 신뢰한 발급자의 키로 검증하고 발급자·대상 서비스·고정 주체·유효기간을 별도로 확인합니다. 워크로드와 Apps Script 실행 주체를 배포 시 허용 목록에 고정합니다. 직원 토큰과 범용 사용자 ADC는 이 호출 자격으로 사용할 수 없습니다.
3. 대상 원장 ID, 출석 프로젝트·DB·리전·컬렉션, 승인 예약 범위는 서버 구성에서 결합합니다. 명령은 범위, 예약 ID, 확정 등원 이벤트 ID, 발행 시각과 만료 시각을 전달합니다. 허용 기간은 60초 이내이며 서비스 자격은 요청 만료 시각까지 유효해야 합니다. 브라우저에서 원장, 상품·이용권 ID 또는 등원 증거를 지정할 수 없습니다.
4. 출석을 다시 읽어 첫 이벤트가 해당 예약의 확정 등원인지 확인합니다. 미래 이벤트, 다른 이벤트, 출석 문서 및 예약 상태 불일치를 차단합니다. 50단계 포트는 검증된 주체·서명 확인 결과를 반환하는 어댑터를 주입받으며 실제 원격 서명 검증기나 배포는 포함하지 않습니다.
5. 동일 요청의 진단 재조회는 읽기만 수행합니다. 쓰는 경로를 승인하게 되면 원장 범위와 예약 ID로 멱등 키를 만들고 이벤트 ID를 상관관계로 기록합니다. 같은 원장을 수정하는 수동·자동 실행은 동일 Apps Script 잠금을 사용해야 합니다. 결과가 불명확한 쓰기는 재발송하지 않고 원장과 이력을 조회합니다. 정정은 별도로 승인된 관리자, 사유 및 감사 이력이 필요합니다.

### 가능한 배포 방식

- **전용 Workspace 실행자와 Apps Script API 실행 배포**. 공유된 표준 Cloud 프로젝트, API 실행 배포와 별도 OAuth 사용자 승인이 필요합니다. Apps Script 실행 API는 서비스 계정 직접 호출을 지원하지 않으며 스크립트 전체에 필요한 범위를 요구합니다. 대상 스크립트의 전체 범위와 배포 실행자, 회사 정책의 승인을 확인한 뒤만 선택할 수 있습니다. [Apps Script 실행 API 요건](https://developers.google.com/apps-script/api/how-tos/execute)
- **인증된 중계 서비스와 Apps Script의 승인된 작업 조회**. 직원 서버 워크로드가 대상 서비스용 신원 증명으로 중계 서비스에 제출하고, 지정된 Apps Script 실행자가 작업을 조회하는 방식입니다. Apps Script 쪽 작업 조회에는 별도 Google OIDC 실행자와 허용 대상 확인이 필요합니다. 설치형 실행을 쓴다면 생성자 계정으로 실행되므로 소유권·운영시간·중단 및 감사를 먼저 승인해야 합니다. 중계가 원장에 직접 쓰면 기존 잠금이 적용되지 않으므로 원장 쓰기는 동일 스크립트에 한정합니다. [Cloud Run 서비스 인증](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) · [Apps Script에서 Cloud 서비스 연결](https://developers.google.com/apps-script/guides/services/cloud-run) · [설치형 트리거](https://developers.google.com/apps-script/guides/triggers/installable)

### 51단계 권장안

**인증된 중계 서비스에 접수하고, 기존 운영 Apps Script 프로젝트의 승인된 Workspace 실행자가 작업을 가져가는 방식**을 선정했습니다. 직원 서버와 Apps Script 실행자의 신원을 분리할 수 있고, 직원 서버에 운영 Apps Script 사용자 OAuth 갱신 자격을 두지 않아도 됩니다. Apps Script 실행 API를 직접 사용하면 별도의 API 실행 배포와 공통 표준 Cloud 프로젝트가 필요하고, 승인된 사용자 자격이 해당 스크립트 전체 범위를 포함해야 합니다. [Apps Script 실행 API 요건](https://developers.google.com/apps-script/api/how-tos/execute)

1. 직원 서버는 기존 Firebase 검증이 끝난 출석 이벤트만 중계 서비스에 접수합니다. 중계는 직원 서버의 전용 워크로드와 Apps Script 실행자의 Google 주체를 각자 검증합니다. 발급자·서명·대상·주체·만료를 확인하고, 접수 권한과 작업 조회 권한을 분리합니다. 브라우저는 중계나 운영 원장을 호출하지 않습니다. [Cloud Run 서비스 인증](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) · [Apps Script에서 Cloud 서비스 연결](https://developers.google.com/apps-script/guides/services/cloud-run)
2. 승인된 실행자가 **수동 차감과 같은 Apps Script 프로젝트**에서 작업을 가져갑니다. 승인된 원장과 예약·이벤트 범위를 다시 검증하고, 수동·자동 모두 같은 `LockService.getScriptLock()` 안에서 예약과 이용권의 최신 이력 및 잔여를 확인합니다. 중계는 이용권 원장을 수정하지 않습니다. 자동 실행에 설치형 트리거를 사용한다면 승인된 실행자 계정으로 설치해야 합니다. [Apps Script 잠금 범위](https://developers.google.com/apps-script/reference/lock/lock-service) · [설치형 트리거와 실행자](https://developers.google.com/apps-script/guides/triggers/installable)
3. 원장 범위와 예약 ID로 접수·발송을 한 번만 허용하고, 확정 이벤트 ID를 증거에 연결합니다. 중계가 미발송 작업을 최초 인도할 때 출석을 다시 확인하고 60초 이내의 작업 증명을 발행합니다. 발송이 있었는지 또는 결과가 불명확하면 사람 검토와 원장 읽기로 넘깁니다. 설치형 작업 조회의 대기 시간과 제한, 실행자 교체, 접근 차단, 긴급 중단, 감사 및 경보의 운영 책임을 사전에 정해야 합니다.

권장안은 **현 설정에서 실행 BLOCKED**입니다. 저장소에는 격리 clasp 대상과 Apps Script 소스만 확인됐고, 활성 CLI 사용자 및 기본 사용자 ADC는 운영 원장 소유자 승인이나 운영 실행 주체의 증거와 연결되지 않았습니다. 두 서비스의 실제 주체·배포·호출 경로와 Apps Script에서 중계로의 네트워크 및 허용 대상을 확인해야 합니다. 외부 진단 엔드포인트 공개, 새 권한 요청, 기존 IAM·OAuth·배포 수정은 수행하지 않았습니다.

## 52단계 통합 테스트 원장 진단

52단계는 사용자가 지정한 통합 테스트 파일과 reader 서비스 계정 권한을 코드 범위에 결합했습니다. Codex 실행 환경은 해당 reader 신원으로 인증된 상태가 아니므로 실제 Google API 요청을 실행하지 않았습니다. 기본 사용자 ADC나 파일 소유자 계정을 reader 서비스 계정으로 간주하지 않습니다. 실데이터 검사 결과는 BLOCKED이며 이 단계의 진단 결과는 합성 데이터에만 적용됩니다.

읽기 어댑터는 예약·등하원관리, 이용권관리, _이용권변동이력의 명시된 전체 열만 읽습니다. 반려견명, 비고, 상품명, 금액, 처리자 및 사유 값은 어댑터 반환 전에 제거합니다. 정합성 분석은 개인별 값 대신 A–T 코드와 오류 건수만 반환하며 쓰기 포트를 갖지 않습니다. 테스트 파일 `Etc/GMT` 시간대를 검증하고, 달력일과 변동 시각을 별도 규칙으로 정규화합니다.

A–S는 내부 ID, 예약·이용권·반려견 연결, 명시적 상품 카탈로그, 잔여 산식, 결제와 이용기간, 이력 중복·연속성, 수동·자동 충돌 및 예약·출석·차감 상태를 집계합니다. 실제 상품 ID와 8·12·16·20회 매핑은 확인하지 않았고 추정하지 않습니다. T는 Firestore와의 대조입니다. 이번 단계에서 허용된 클라우드 조회는 테스트 Sheets뿐이라 Firestore는 읽지 않았으며 실데이터 T는 BLOCKED입니다.

## 51단계 읽기 어댑터

`staff-pass-ledger-read.js`는 독립적으로 확인된 읽기 주체에 결합한 `drive.files.get`과 `sheets.spreadsheets.get`만 주입받습니다. 승인 기록에는 운영·격리·합성 환경별로 서로 다른 파일 ID, 읽기 주체, 예약 허용 목록, 범위와 만료가 필요합니다. 요청이 임의 원장이나 열을 지정하면 API에 전달하기 전에 차단합니다. 실환경에서 이 어댑터를 쓰려면 해당 소유자가 이미 승인한 뷰어와 Drive 버전 메타데이터, Sheets 읽기 범위가 필요합니다. [Drive 읽기 전용 메타데이터](https://developers.google.com/workspace/drive/api/guides/file-metadata)

- 51단계의 최소 열 집합은 합성·기존 계약을 위한 기준이었습니다. 52단계 통합 테스트 원장 검증에서 전체 스키마 헤더를 검사하기 위해 예약 `A1:K`, 이용권 `A1:O`, 이력 `A1:J` 세 범위로 고정했습니다. 승인 행 범위는 각 시트의 전체 그리드 행을 포함해야 합니다. 예약 허용 목록은 진단 대상을 제한하며 API에서 전체 행 범위를 읽는 권한을 대신하지 않습니다.
- Drive에서 파일 ID, 스프레드시트 유형, 버전 및 편집 가능 여부를 확인하고 Sheets에서 환경별로 고정된 시간대와 세 GRID 시트를 확인합니다. 통합 테스트 파일은 확인된 `Etc/GMT` 메타데이터를 요구합니다. 달력 날짜 값은 ISO 날짜로 보존하고, 변동이력 시각은 GMT 기준 ISO 시각으로 변환합니다. 날짜 비교는 별도 정책에 따라 Asia/Seoul 달력일로 처리합니다. 고정 범위의 그리드 값은 한 번 읽은 뒤 시트 크기와 Drive 버전을 다시 확인합니다. 제한 시간 초과, 버전·크기 변경, 수식·계산 결과는 판정을 폐기합니다. [Drive 파일 버전](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) · [Sheets 범위와 필드 마스크](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get) · [Sheets 원시 값과 계산 값](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/cells)
- 진단은 승인된 상품 ID가 가리키는 정확한 8·12·16·20회 값을 사용합니다. 상품 분류나 회차가 불명확하면 검토가 필요합니다. 수동 감사 행의 담당자·사유는 조회 결과에서 제외하고, 자동 차감 이력은 예약과 연결된 작업 증명만 대조에 사용합니다. 외부 결과는 고정 상태와 사유 코드, 필요 시 회차 예측만 반환합니다.

## 실행 가능한 합성 진단

저장소 루트에서 다음 명령을 실행합니다.

```powershell
node guardian-auth-server/run-staff-pass-dry-run.cjs --synthetic
node --test guardian-auth-server/staff-pass-dry-run.test.js
node --test guardian-auth-server/staff-pass-ledger-read.test.js
```

첫 명령은 여섯 합성 사례의 판정·사유 건수와 정기권 잔여 8회에서 7회로의 예상 결과만 출력합니다. 진단은 원장 쓰기 모듈을 불러오지 않으며, 읽기 포트와 49단계 자동 차감과 공유하는 순수 판정 함수만 사용합니다.

- `ELIGIBLE`은 현재 조회 자료에서 차감 가능성을 의미합니다. 운영 쓰기 승인이나 성공의 증거로 사용할 수 없습니다.
- `NOT_REQUIRED`는 확인된 일일권입니다. 일일권 정산은 별도 정책입니다.
- `COMPLETED`는 기존 수동 또는 이벤트와 일치하는 자동 차감이 원장에서 확인된 경우입니다.
- `NEEDS_REVIEW`는 미연결·누락·중복·정합성 오류·이전 발송 흔적 또는 하원 뒤 미완료 등입니다. 안전하게 조회할 수 있는 범위에서 관리자 확인이 필요합니다.
- `BLOCKED`는 인증·대상·스키마·읽기 실패나 시간 제한입니다. 다른 계정으로 전환하거나 다시 요청하지 않습니다.

## 실원장 검증 선행 조건

기존 소유자 승인에서 운영 원장, 허용 시트와 열, 예약 범위, 읽기 주체 및 뷰어 권한을 확인한 뒤 원장 점검을 실행합니다. 먼저 실제 변동이력 헤더, 상품 ID와 8·12·16·20회 매핑, 예약 연결, 중복 및 잔여 불일치의 익명 건수를 확인합니다. 권장 배포안의 실제 서비스 주체와 인입 경로, 기존 프로젝트의 공통 잠금, 부분 실패 및 정정 책임의 승인은 별도입니다. 운영 활성화·실환경 차감·복구 역시 개별 승인 대상으로 유지합니다.
